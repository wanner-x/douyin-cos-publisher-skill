# 抖音 COS 发布助手

把用户指定素材整理成可复核、可发布、可追踪的抖音内容。默认账户约定与合集规则见 [references/account.md](references/account.md)。进入抖音发布页、编辑已发布作品或做发布后验收前，读取 [references/publish-ui.md](references/publish-ui.md)。用户手动发布、定时发布或要求后续处理/原图归档时，再读取 [references/post-publish.md](references/post-publish.md)。

## 执行边界

- 优先操作当前已登录的抖音客户端，包括客户端内部的创作者中心。用户指定“使用 App”时持续遵守；读取超时不代表可以改用外部浏览器。
- 不导出 Cookie，不安装反检测工具，不绕过验证码、风控或登录验证。遇到验证时停下交给用户。
- 可以自动检查素材、查证角色、起草文案、填写发布页和完成只读校验。
- 上传本地文件、公开发布、修改公开作品或合集都属于对外操作；分别遵守用户已有授权的范围。先列明精确素材和发布方案，获准上传后填写草稿；最终公开发布前展示实际填写的清单并取得确认。一次确认可以覆盖清单中明确列出的连续发布及分类动作；清单外的新批次必须重新确认。
- 发布结果不明确时，先到作品页核对；禁止直接重试，以免重复发布。
- 发布成功后移动或归档原素材，需要用户明确授权；当前会话或账户约定中已有的授权持续有效，不重复询问。只能在作品明确显示“已发布”、目标合集已核验且成品原文件名单准确时移动；“定时待发布”“正在发布”“审核中”或结果未知时禁止移动。

## 强制工作流与状态门槛

自行执行发布时按以下流程推进；用户已手动提交时从核验实际作品接续，不重新上传或发布：

`方案已生成 → 草稿已填充 → 用户已确认 → 已提交 → 已发布状态确认 → 合集验收通过 → 素材已归档`

- **方案已生成**：已完成视觉分组、图片顺序、标题、正文、5 个标签候选、配乐和目标合集。用户要求“先生成全部方案”时，到此停止，不预填或发布。
- **草稿已填充**：在已登录的抖音客户端完成上传与填写，并通过发布前复核；此状态仍不得点击发布。
- **用户已确认**：把最终清单展示给用户，并在点击发布的紧邻步骤取得明确确认。用户确认的是这组具体图片和最终文案，不是以后所有批次的长期授权。
- **已提交**：只点击一次发布。页面显示“正在发布”或跳转不能算成功；结果不明时去内容管理核对，不重复点击。定时作品另记“已提交定时、等待发布”，记录绝对日期、时间及其时区。
- **已发布状态确认**：锁定准确作品，管理状态明确为“已发布”。优先使用作品 ID，再结合发布时间、正文、首图和图片数；标题留空时不依赖标题搜索。用户手动修改造成差异时记录实际成品，不能自动判作另一作品或沿用原名单。
- **合集验收通过**：目标作品在正确合集内，且状态为“通过/已发布”。合集总数变化或最新条目作为辅助，不能仅凭总数增加推断作品已入合集。
- **素材已归档**：用户已授权，发布状态与合集均确认，成品原文件名单明确后，移动精确原文件并验证源、目标两端。内容异常单独记录，不等于发布状态未知；具体处理见发布后参考。

为每个批次保留执行记录：作品 ID、提交方式、实际发布时间、发布状态、内容核验结果、合集状态、归档授权与状态、实际正文/话题/配乐，以及计划文件、实际上传文件、成品文件。三份文件名单不得互相覆盖。状态不明确时写“结果未知需人工核对”。

## 1. 盘点与视觉分组

1. 解析用户给出的文件、文件夹或角色范围。未指定时使用账户参考中由使用者配置的待发布目录；若尚未配置，先请用户提供目录。
2. 只读扫描 JPG、JPEG、PNG、WebP、HEIC、MOV、MP4。需要清单或缩略图时运行：

   ```bash
   python3 "{baseDir}/scripts/prepare_media.py" --source "<绝对路径>" \
     --manifest /tmp/douyin-media.json \
     --contact-sheet /tmp/douyin-contact-sheet.jpg
   ```

   如果系统 Python 没有 Pillow，使用当前环境提供的图像运行时；不要为盘点素材临时安装依赖。
3. 逐图检查，按“同一角色/IP + 同一套服装 + 同一拍摄场景”分组。目录名、文件名、拍摄时间仅作辅助，不能代替视觉判断。
4. 角色不清晰时，先根据服装、武器、徽记、发色、场景文字和已有作品线索检索公开资料。仍无法可靠确认时使用中性描述并标注“待确认”，不要猜角色名或 IP。
5. 排除明显失焦、闭眼、重复连拍、严重遮挡和构图失衡的图片；不要删除或移动原文件。
6. 每组选择一张人物清晰、识别度高、构图完整的首图。其余图片按全身、半身、特写和动作变化排序，避免连续近似机位。

## 2. 拆分批次

- 同一角色图片数不超过 4：发 1 条。
- 同一角色图片数大于 4：必须且只拆成 2 条，数量尽量均衡；奇数时第一条多 1 张。例如 5 张拆成 3+2，9 张拆成 5+4，18 张拆成 9+9。
- 两条分别使用不同首图、不同构图节奏和不重复的文案角度；标题用“氛围/角色魅力”和“动作/场景细节”等不同切口，不使用机械的“上/下集”，除非用户要求。
- 不跨角色混发。不能为了凑数量把不确定角色塞进同一批次。

## 3. 生成文案、标签与声音

为每个批次生成一份发布卡片。若本机存在 `cos-douyin-wanxiang`，文案、Tag 候选和配乐必须先按该技能生成或复核；用户对文案的修改优先。`douyin-cos-publisher` 负责发布约束、界面落地和验收，不把另一个技能的候选 Tag 直接当作已生效话题。

- `角色/IP`：确认来源，并记录置信度；不确定时写明待确认。
- `标题`：可选。一句自然、有画面感的中文标题，优先角色名 + 情绪钩子，避免堆砌形容词、夸大和模板腔；若标题与正文开头重复，就留空。
- `正文`：1–3 句，先落到角色独有的身份、设定、关系或语气，再用场景和构图补充画面；动作复述不能替代角色表达。可加一个轻量互动问题；不要虚构展会、摄影师、Coser、地点或授权关系。
- `标签`：固定输出 5 个。内容属于二次元时，必须包含 `二次元`，其余位置再从 IP、角色、角色 COS、作品 COS、场景或摄影类型中择优补足；非二次元内容不要机械添加。只用真正相关的标签，不蹭无关热点，不重复同义标签。发布卡片中的名称只是候选；实际填写时必须通过发布页的话题选择器逐个选中，不能把直接输入的 `#文字` 当成已生效话题。
- `配乐`：图文默认匹配抖音曲库中的配乐。优先搜索 2–3 个候选，试听后按角色气质、当前照片和节奏选择；记录实际曲名、作者/版本、时长及选择理由。用户要求参考同角色作品时，查看可访问的近期作品作为候选线索，不把个别作品用歌当作普遍趋势。用户指定配乐时优先核对该曲，不擅自替换；具体版本在发布当日核验。
- `旁白`：用户说“配音”且需要人声叙事时，生成 8–20 秒、60–100 字的旁白稿，并将图片制作成竖屏轮播视频后再走视频发布流程。纯图文默认把“配音”理解为配乐；若用户明确要 TTS，则不得只选 BGM 代替。
- `合集`：按账户参考中的优先级选择一个主合集。除非用户要求，不重复加入多个合集。

查找角色资料、当前热门话题或曲目时使用公开搜索，并优先官方/权威来源。热点和音乐会变化，发布当日重新核对。

## 4. 发布前复核

在抖音页面完成填写但不发布，然后同时检查：

- 当前账户与目标账户一致；
- 发布类型正确（图文或视频），图片顺序和数量与发布卡片一致；
- 素材已上传完毕，没有裁切异常、黑边、重复或漏图；
- 标题、正文、标签与计划一致，没有把文件名或内部备注发出去；
- 正文在富文本编辑器和发布预览中都完整可见；不得用直接赋值覆盖非空富文本编辑器；
- 每个标签都已从话题候选列表中选中并成为话题实体；只有普通 `#文字` 不算通过；
- 话题实体总数不超过 5；若内容属于二次元，列表中包含 `二次元`；
- 分别核对预览中的正文和话题，不能只看编辑器字数或输入框内容；
- 配乐可播放且与计划一致；视频旁白存在时检查音量和字幕同步；
- 可见性、位置、声明、原创等设置没有被意外改变；
- 作品此前没有成功发布。

将最终内容冻结为一份确认清单：账号、图片数量与精确文件名、首图、标题（留空也写明）、正文、5 个话题、配乐版本、合集、公开范围和发布时间。定时发布把“明天”等表达换算为绝对日期、北京时间，并核对页面实际设置。向用户展示该清单并取得确认；确认后由助手更改任何实质字段，必须重新展示并再次确认。

## 5. 发布与结果判定

1. 获得确认后逐条点击发布，每次只处理一个批次。
2. 点击后先记录为“已提交”。定时作品记录“已提交定时、等待发布”；只有作品管理明确为“已发布”才确认发布状态，成功提示或页面跳转只作为辅助证据。
3. 若状态为审核中，记录为“已提交、审核中”，不要重复发布，也不要移动原素材。
4. 若点击后结果未知，立即到作品页按首图、标题和时间核对；仍未知则停止后续批次并报告，不重试。
5. 一条失败不应导致已经成功的批次再次发布。
6. 用户说“我已手动发布/已审核发布”时，进入发布后核验；用户补改的正文、出镜账号、话题、音乐或图片均按成品记录，不重新提交原方案。

## 6. 发布后内容验收与归类

1. 到内容管理优先按作品 ID 锁定本次作品，再用正文、首图、图片数和发布时间排除同名或旧作品；标题留空时不依赖标题搜索。
2. 状态为“审核中”时等待或稍后刷新；不得移动素材，也不得重复发布。状态明确为“已发布”后再继续。
3. 核对发布后的标题和完整正文；确认 5 个话题全部显示且能作为话题实体/链接识别。缺正文、话题为普通文本、话题少于计划或超过 5 个时，记录异常，不自动编辑已公开作品。
4. 按发布卡片指定的主合集归类。若发布前已经选择合集，仍需进入合集管理做事后验收。
5. 用作品 ID 或首图、正文和发布时间锁定合集中的本作品，确认状态为“通过/已发布”；补处理旧作品时无需它仍是最新一条。合集名称、“第 N 集”或总数变化不能单独证明归类成功。
6. 分别报告发布状态（定时待发布/审核中/已发布/未发布/结果未知）、内容核验（符合方案/存在差异/未核验）、合集和归档结果，避免一个笼统状态掩盖未完成项。

## 7. 发布后素材归档

用户已授权“发布后移动/归档”时纳入必要收尾；缺少授权时报告“待授权归档”。详细文件映射和异常处理见 [references/post-publish.md](references/post-publish.md)。

1. 锁定准确作品，确认“已发布”；分别记录实际内容与计划差异。
2. 若要求归入合集，核验准确作品在目标合集且状态为“通过/已发布”。
3. 列出成品实际使用的精确原文件，检查源文件及目标同名冲突；禁止宽泛通配符，也不得直接照搬历史上传名单。
4. 移动这些原文件，再核对源端消失、目标端完整、SHA-256 与移动前一致；禁止覆盖同名文件。
5. 任一步结果不明确或仅部分成功时立即停止并报告；不要扩大范围或盲目重试。

归档完成后更新执行记录。不得先写“已归档”再移动文件，也不得因为发布按钮已点击就把素材视为已发布。收尾报告必须列明发布状态、内容差异、合集、归档结果和剩余文件；授权归档未完成时给出具体阻塞原因，不能笼统报告“后续处理完成”。

上传时产生的临时 ASCII 文件只是副本，不能当作已归档的原素材。

## 8. 当前素材目录的额外规则

默认目录可能是平铺结构，不假设子文件夹代表分组。每次重新盘点实际文件，不沿用上次图片数量。对用户当前的明确偏好始终遵守：同一角色超过 4 张时拆成两次发布。
